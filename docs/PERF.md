# 性能评估：热点在哪，要不要用 C++/Rust/WASM 重写

结论先行：**不值得。** 实测热点不在 JS 计算，而在三类"已经够快且天然在 C/C++ 里"的地方——文件写入（IO）、SQLite 的 FTS/bm25 排序、ONNX Runtime 推理。纯 JS 的三处算法（规则抽取、冲突裁决、余弦全扫描）在真实库规模下是亚毫秒级；只有在 3 万条、且明文犟在 512 维全量扫描时，余弦扫描才涨到 ~39 ms，用 SIMD 顶多省 30 ms/次——相对一次 LLM 往返（数百 ms 到数秒）不可见，而代价是每个平台一份预编译二进制或一套 MSVC/VS 构建工具，直接毁掉"零硬依赖、`npm i` 不编译"的卖点。

## 2. 测量口径

- 写入管线：`bench/test-p1` 同款 DDL（`memory` + `memory_vec` + `memory_fts`，`journal_mode=WAL`、`synchronous=NORMAL`），每条事实 = 1 次 md 落盘 + 1 次 memory insert + 1 次 fts insert + 1 次 512 维向量 BLOB insert。
- FTS 查询：`memory_fts MATCH ? JOIN memory ... ORDER BY bm25 LIMIT 50`，6 个查询词轮转 200 次；语料里约 **1/6 的行**命中查询词（高频词的最坏情形，不是选择性查询）。
- 向量检索：`Float32Array` 全量载入后 JS `cosine` 线性扫描 + 排序，20 轮。
- 抽取/裁决：真实 `p1.js` 导出函数，240 行中文对话（产出 180 条事实）；`decideConflict` 20000 次。
- 环境：NVMe SSD、单进程、无并发写；**合成语料**，不代表 10 万条以上的真实库。

## 3. 分项实测

单位 ms，p50 / p95。

| 环节 | 1,000 条 | 10,000 条 | 30,000 条 | 结论 |
|---|---|---|---|---|
| md 文件写入（每条） | 0.63 / 1.17 | 0.70 / 1.33 | 0.76 / 1.39 | 随规模几乎不变 → **IO 常量** |
| DB 写入（memory+fts+vec，每条） | 0.17 / 0.34 | 0.18 / 0.52 | 0.20 / 0.56 | 走 WAL，比落 md 快 ~4 倍 |
| **写入合计（每条）** | **~0.80** | **~0.88** | **~0.96** | md 写入占 80%+ |
| FTS 查询（高频词） | 0.20 / 0.32 | 7.49 / 9.33 | 23.99 / 39.25 | 1k→10k 超线性（10 倍行数 37 倍耗时），主因 bm25 排序 + 回表 join |
| 向量全量载入（进程启动） | 7.3 | 63.7 | 369 | 一次性代价，之后命中内存 Map |
| 向量余弦全扫描 + 排序（512 维） | 0.56 / 1.19 | 8.13 / 9.78 | 38.92 / 55.50 | 线性；**唯一有优化空间的 JS 热点** |
| 嵌入推理（ONNX，模型热） | — | — | — | 1.58 / 2.66 ms/次（512 维，含缓存） |
| 模型加载（首次） | — | — | — | 223 ms，进程生命周期一次 |
| 规则抽取 `ruleExtract`（240 行 → 180 条） | — | — | — | 0.61 / 1.27 ms/次（mean 0.95） |
| 冲突裁决 `decideConflict` | — | — | — | **0.001 / 0.002 ms/次**（1 µs） |

读法：一次"混合检索"的总耗时 ≈ FTS 查询 + 余弦扫描 + 嵌入（若查询需要转向量）。在 1 万条规模下约为 `7.5 + 8.1 + 1.6 ≈ 17 ms`；在 10 万条规模下按线性外推约 100 ms+，此时才需要动结构（先 FTS 预筛再算余弦，或做增量索引），而**不是换语言**。

## 4. 分析与结论

### 4.1 写入管线：瓶颈是 IO，不是 JS

每条事实 0.8–0.96 ms，其中 md 落盘 0.6–0.8 ms、SQLite 三张表 0.2 ms。JS 侧只做字符串拼接与参数绑定，占比可以忽略。把这段搬进 Rust 只能省 SQLite 之外那点胶水，同时必须自己实现 md 落盘语义（frontmatter、脏位、restore）——纯风险。

### 4.2 FTS 查询：瓶颈在 SQLite 内部，已经是最优语言

`bm25()` 排序必须扫完所有命中行的倒排表并排序，这是 SQLite 的 C 代码在做。JS 侧只等结果。3 万条、高频词 24 ms 的代价来自**查询形状**（无选择性 + LIMIT 50 仍需全排序），不是解释器慢。真要优化，顺序是：先用 `LIMIT` 提前截断/加覆盖率过滤、给 `subject/predicate` 加组合索引、对超高频词做停用词——都在 SQL 层，与是否原生无关。

### 4.3 向量检索：唯一值得讨论的一项，仍然不划算

- 512 维全量扫描在 3 万条要 39 ms。JS 标量余弦受限于单线程与边界检查，SIMD 版（Rust/WASM/SIMD.js）乐观估计快 3–5 倍，即省 25–30 ms。
- 但这 39 ms 出现在"库已 3 万条"才发生，且一次会话每轮最多调一两次检索；同一轮里 LLM 往返是 500–2000 ms。**省 30 ms 等于 1.5–6% 的不可感知开销**。
- 而代价是明确的：每个平台（win32-x64 / darwin-arm64 / linux-x64…）一份预编译二进制，或要求用户装 MSVC/VS Build Tools + node-gyp。这与"`npm i` 不编译、装上就能跑、零硬依赖"直接冲突——而那正是这个插件最大的安装优势。
- 可逆的折中（若将来真需要）：把余弦扫描的候选集先用 FTS 预筛到几百条，或提供**可选**的 WASM SIMD 加速包，默认不装。不要做成 C++ 核心。

### 4.4 其余两项都在预期内

- 嵌入推理 1.58 ms/次，已是 ONNX Runtime（C++）在跑，不是 JS 能改的部分。
- LLM 抽取默认关闭；一旦开启，一次网络请求就是数百 ms 到数秒，比上述所有 JS 计算高 2–3 个数量级。任何"本地计算优化"在这条路径上都没有意义。

### 4.5 最终判断

| 问题 | 回答 |
|---|---|
| 瓶颈在 SQLite/IO/LLM 还是 JS 计算？ | **IO（md 落盘）+ SQLite FTS 排序为主，ONNX 推理次之；JS 计算在真实规模下 <1 ms** |
| 用 C++/Rust/WASM 重写核心值不值？ | **不值**。预期收益 ≈ 每次检索省 0–30 ms，成本是多平台构建链 + 丢失零依赖安装 |
| 用 VS Code 编译器/MSVC 重写？ | **更不值**。要求用户具备本地编译环境，恰好是插件要避免的失败模式 |
| 什么情况下要重新评估？ | 单库 >10 万条、或检索 P95 影响交互（>100 ms）时：先做候选集预筛与增量索引，再考虑可选加速包 |

## 5. 复现说明

测量脚本为一次性临时文件（`node bench/...` 之外的独立脚本），未提交到仓库，以免污染 `files` 字段与包体积。需要复现时按第 2 节口径重建：DDL 从 `bench/test-p1.js` 复制，向量用随机单位向量（只为测扫描成本，不为测精度），嵌入项用 `embed.js` 的 `Embedder` 指向本地已缓存模型。所有数字为单次抽样（每项 20–200 轮取 p50/p95），不同机器绝对值会变，**量级与占比关系稳定**。
